## 1. Scope & Build Order

Phase 1.5 is one spec, four chunks, implemented and shipped **in this order** (each chunk lands green on main and deploys before the next starts; chunk B ships in batches):

1. **A — Sim per-question attempts** (+ two parked stats fixes on the same code path)
2. **B — Probability/EV bank** (150 problems, walkthroughs, verification pipeline, drill UI)
3. **C — Leaderboards** (user-vs-user, per timed preset)
4. **D — Review queue** (SRS on misses, re-rolled numbers)

Each chunk gets its own implementation plan.

## 3. Chunk A — Sim Per-Question Attempts

**Problem:** timed sims write only a `TestSessionRow`; sims-only users see empty accuracy/pace/streak panels, and sims can never feed the review queue.

**Change:** when a sim finishes, the runner emits one `AttemptRow` per **answered** question in the same save as the session row: generator problem id + seed, `mode: "test"`, topic, given answer, correct flag, per-question `timeMs` taken from the timings array already captured, `sessionId` linking to the session. Skipped questions produce **no** attempt row (skipping is strategy, not a miss) but remain counted on the session row. Persistence goes through the existing store (local + Supabase) with its existing outage-queueing. Volume is fine: ~80 rows per Optiver sim against the newest-5000 remote cap.

**Bundled parked fixes (same code path):**
- Add `total int` to `test_sessions` (migration + `TestSessionRow` type + both stores), so non-standard `?count=` runs can be excluded from/normalized in score bars, and so chunk C's view can sanity-check `score ≤ max achievable for total`.
- Include the sequences-sprint preset in the dashboard score chart/benchmark render.

Old sessions are not backfilled — the per-question data doesn't exist.

## 4. Chunk B — Probability/EV Bank

### Content model
Typed TS templates in `content/problems/<topic>/`, exactly the parent-spec §6 shape with one refinement: because templates are TS modules (not JSON), `answer` is a **plain function of the drawn params** — no string-expression evaluator exists or is built. Six topics with target counts (150 total):

| topic | count |
|---|---|
| counting | 25 |
| bayes (conditional/Bayes) | 30 |
| ev-variance | 30 |
| distributions | 25 |
| ruin (gambler's ruin / random walks) | 20 |
| geometric (geometric probability) | 20 |

Difficulty mix ≈ 40% L1 / 40% L2 / 20% L3 per topic. Sources and the transformation rule per parent §6; lineage recorded in the `source` field. Every number appearing in walkthrough text interpolates from params/derived values. KaTeX for all math.

### Engine additions (pure TS, TDD)
- `drawParams(template, seed)`: `choices` lists, numeric `range`s, `clean` constraint for round numbers; deterministic per seed.
- Grading honors per-problem `accepted.tolerance` (`{rel}` **or** `{abs}`, always explicit).
- Parser extended beyond plain-number/fraction: percents (`12.5%`) and small arithmetic expressions (`1/6 + 1/3`, parentheses, `+ − × / ^`) via a small recursive-descent evaluator. No `eval`.

### Verification pipeline (CI gate)
1. TS script draws ~100 instances per problem → `instances.json`: params, computed answer, and every interpolated solution number.
2. Python `verification/` suite recomputes each instance **independently from the params alone**: per-problem (or per-family, parameterized) Python solvers — seeded Monte Carlo with trial counts scaled to event rarity, or SymPy exact for closed forms (`verify.method` per problem). Rare-event problems must use `symbolic`.
3. Parent-spec checks split by side: the TS emitter validates KaTeX compiles and no un-interpolated params remain; the Python suite enforces tolerance not loose relative to answer magnitude.
4. New CI job runs the suite; **red = no deploy**. Every shipped batch includes its Python counterparts — this is the accepted cost of "zero unverified answers."

### Drill UI
`/drills/probability` with topic + difficulty filters; keyboard-first flow identical to existing drills. On submit the walkthrough unfolds per parent §5, in order: verdict line (your answer + exact value) → Setup → numbered KaTeX steps → sanity check → key-insight callout (teal) → common-trap callout (red) → seen-at firms + expected pace → actions (re-roll numbers · harder variant · add to review queue · report issue). Attempts record slug + version + seed, `mode: "practice"`.

### Shipping cadence
Batches of ~25–30 problems grouped by topic; each batch = templates + walkthroughs + Python verifiers together, CI green, deploy. Infra (engine, parser, UI, pipeline) ships with the first batch.

## 5. Chunk C — Leaderboards

### Backend
One Postgres view (own migration): best server-recorded score per user per preset from `test_sessions ⋈ profiles`, `rank()` window per preset, exposing **only** handle, score, and date. Filters: `not merged_from_local` (forgeable local history never ranks, per parent §7) plus sanity predicates (score within the preset's achievable range given `total`, duration within preset bounds). The existing partial index `test_sessions_preset_score … where not merged_from_local` serves it. Supabase pattern: definer-owned view, `select` granted to `anon` + `authenticated`; underlying RLS tables stay locked. Deeper anti-cheat remains as parent §7 states it (accepted limitation; revisit only if leaderboards gain stakes).

### Page
`/leaderboard`, editorial per the design system: preset switcher (Optiver 80-in-8 · sequences sprint · …), dot-leader ranked list in mono, benchmark thresholds from the `benchmarks` table woven in as labeled divider rows citing provenance ("— 55 · invite zone · publicly reported —"), **never** as fake user rows. The signed-in user's row is highlighted, pinned at the bottom when off-screen. Anonymous users see the full board plus the sign-in nudge ("your local scores don't rank"). Command bar gains the link.

## 6. Chunk D — Review Queue

### Data
`ReviewRow { problemId, topic, dueAt, intervalDays, ease, addedAt }`, mirrored across the existing local/Supabase store pattern; the `review_queue` table already exists (PK `(user_id, problem_id)`, `ease` default 2.5). Anonymous users get the full queue in localStorage; it merges on sign-in — dedupe by `problemId`, keep the earlier due date.

### Intake
- **Auto:** any wrong answer in drills or sims upserts the problem (immediately due, interval 1). Sims: answered-wrong only; skips never enqueue.
- **Manual:** the drill "add to review queue" action upserts the same way.
- The queue page allows removal.

### Scheduling (SM-2-lite)
- Correct on review: `interval ×= ease`; `ease += 0.05` (cap 2.8).
- Wrong on review: `interval = 1`; `ease −= 0.2` (floor 1.3).
- `dueAt = now + interval` days.

### Review mode
`/review` shows the due count and upcoming list (with remove). "Start review" runs the standard drill flow over due problems with **re-rolled numbers** — arithmetic/sequences regenerate from their generator ids, prob/EV redraws params from a fresh seed — so numbers are never memorized. Grading updates SRS state and records attempts with `mode: "review"` (already in types and DB check constraint), so reviews appear in stats.

## 7. Testing & Rollout

- Engine, parser, and SRS logic test-first (vitest).
- Python verification suite gates all content in CI (new job).
- Playwright smoke gains two flows: (1) timed sim → per-question attempts visible in stats; (2) answer wrong → problem due in `/review` → complete a review.
- Rollout per §1; each chunk green on main and deployed before the next.
