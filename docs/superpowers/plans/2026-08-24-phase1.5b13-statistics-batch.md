# Statistics Batch (B13) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this
> plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take `statistics/*` from 10 templates to ~35, and give it the easy tier it has never
had (currently **zero** d1 problems).

**Why this batch:** the bank is 224 problems and **81% of it is probability** (181). Statistics
and finance sit at 10 each; pure math at zero. Statistics is the thinnest topic that real quant
interviews weight heavily, and it is one of five topics with no easy on-ramp at all.

**Architecture:** No new machinery. Each template is a `ProblemTemplate` in
`content/problems/statistics/`, registered in `content/problems/index.ts`, with a counterpart in
`verification/solvers/statistics.py`. All five existing content gates apply unchanged.

## Non-negotiables, learned the expensive way

These are not style notes. Each one is a gate that has already failed on a shipped batch.

1. **Probe before prose.** `npx tsx tools/probe.ts` measures the parameter space. Run it on every
   design BEFORE writing a word of prose. It exists because two designs were found to produce
   answers of 1e-17, and because statistics templates quote *variances and covariances as
   integers* rather than SDs and correlations — that is what keeps printed terms exact.
2. **Three parameter axes, not two.** `emittedSpread` walks consecutive seeds whose first
   mulberry32 draw is not decorrelated. A 150-tuple two-axis space repeated one tuple 6 times
   against a cap of 4; growing it to 192 did not help. A third axis adds an rng draw and does.
3. **Every printed chain runs over integers.** A rounded intermediate — even a transcendental,
   even an ordinary product like `105 x 0.97 = 101.85` printing as `101.9` — breaks the next
   chain built on it. Recompute from the original literals; never re-use a printed intermediate.
4. **A count answer needs `abs: 0`, never `rel: 0.005`.** At an answer of 1000 a relative band
   accepts 995, and for "smallest n that clears the margin" 995 provably fails the requirement.
   Adding one moves the exact-count pin in `registry.test.ts`.
5. **Round before any ceiling or floor.** `Math.ceil` on 14.000000000000002 returns 15. Round at
   the ninth decimal first. This shipped a wrong answer on 6 of 392 draws once already.
6. **At least one claim-free segment per template**, and >= 2 evaluable chains.
   `printed-precision.test.ts` asserts `claimFree > 0` per topic. State the formula symbolically
   before plugging numbers in — it satisfies the gate and is better pedagogy.
7. **>= 3 bespoke prose claims per template, each with a `breaks` falsifier**, and a 2% answer
   error must be caught. This gate is the one that rejected a textbook line about put-call
   parity that is false whenever money costs anything. No numeric check could have seen it.
8. **`constraint` stays a ONE-LINE arrow.** The registry check is a single-line regex, and a
   module-level helper is only licensed if `constraint` transitively reaches it.

**And the one that outranks all of them:** gates 1-5 check that printed numbers are consistent
*with each other*. **None of them checks the formula is right.** Two shipped formulas passed
every gate and were wrong. Task 4's independent verifier is not optional.

## Decide this first: the topic slug

All 10 existing statistics templates carry the topic **`statistics/moments`** — including the
five regression ones, which already strains the name. A z-test and an order statistic do not
live under "moments" at all.

So before Task 1, decide and write down which of these the batch does:

1. **Keep one topic** (`statistics/moments`) and accept that the label is now just "Statistics".
   Zero registry churn; the per-topic count pin moves once.
2. **Split into three** — `statistics/moments`, `statistics/estimation`, `statistics/inference` —
   re-tagging the existing 10 as part of the batch.

Option 2 reads better and matches how the probability family is already split seven ways, but it
is a re-tag of shipped content: `registry.test.ts` per-topic counts, `TOPIC_LABELS` in
`content/problems/index.ts`, and any stored attempts keyed by topic all move with it. **Note
also that a changed QUESTION needs a `version` bump — a changed TOPIC does not**, so the re-tag
itself is safe for stored attempts; it is the count pins that need care.

Recommendation: **option 2**, done as step 0 of Task 1 while the batch is already touching the
registry, rather than as a separate migration later.

## Task 1: The easy tier (8 templates, d1)

**Files:** `content/problems/statistics/*.ts`, `content/problems/index.ts`

Statistics has no d1 at all. These are the on-ramp: one concept each, integer arithmetic, no
regression.

- [ ] `sample-mean-and-variance` — compute both from a small integer sample. Axes: n, spread, offset.
- [ ] `variance-of-a-scaled-sum` — `Var(aX+b)`. The `b` does nothing; that is the lesson.
- [ ] `covariance-from-a-table` — Cov from paired integer values.
- [ ] `correlation-from-covariance` — Corr from Cov and two variances chosen as perfect squares.
- [ ] `standard-error-of-the-mean` — `sigma/sqrt(n)`, n a perfect square so the chain stays exact.
- [ ] `pooled-mean-of-two-groups` — weighted mean; the trap is averaging the averages.
- [ ] `median-vs-mean-with-an-outlier` — resistance, on an integer sample.
- [ ] `z-score-from-mean-and-sd` — standardisation, integers throughout.

**Design rule for this whole task:** every answer must be exactly representable. Pick variances
as perfect squares and n as a perfect square wherever a square root is printed.

- [ ] **Verify:** `npx tsx tools/probe.ts` on each — >= 12 distinct answers at rel 0.005,
      >= 70 texts/100, max repeat <= 4, >= 300 legal tuples.

## Task 4: The independent verifier — the only gate that catches a wrong formula

**Files:** `verification/solvers/statistics.py`

- [ ] **Step 1:** Write one solver per new template, keyed by problem id.

**The route must not share the template's assumption.** `duplicated-sample-slope-variance` asked
for "the variance of the fitted slope" on duplicated rows; the brute inverted the same doubled
design matrix, shared the same misreading, and agreed with the wrong question. Prefer Monte Carlo
or exhaustive enumeration over re-deriving the closed form the template already uses. Where only
a closed form exists, read the QUESTION against the solution — that is what catches it.

- [ ] **Step 2:** `npm run verify:emit && python3 verification/verify.py`

- [ ] **Step 3: Watch it fail, one template at a time.**

The sequence is always `mutate -> npm run verify:emit -> python3 verification/verify.py`.
Skipping `verify:emit` makes verify.py compare the solver against the PRE-mutation answers, so it
agrees with itself and reports green. Only the first 60 failures print — read the
`VERIFY FAILED — N issue(s)` header for the true count, and mutate ONE template at a time. A
count of 225 per corrupted template (100 derived + 100 answer + 25 brute) is how you know the
independent brute route fired rather than a mirrored `exact`.
