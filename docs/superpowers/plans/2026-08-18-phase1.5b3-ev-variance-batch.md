## Constraints that bite (read before authoring anything)

1. **Never write a literal `$` for currency. This is the only rule here that no gate enforces.** `auditText` (`verification/emit.ts:21-24`) treats `$` as a math delimiter: two currency signs in one sentence give an even count so the parity check passes, and the text between them goes to KaTeX, which accepts it. Verified — `you win $5 dollars; otherwise you lose $3 dollars.` renders `5 dollars; otherwise you lose ` as italic math in the drill and passes every gate green. Write amounts unitless, or spell the unit: `you win ${fmtNum(p.w)} dollars`.

2. **`|answer| <= 1e4` and `|answer| >= 0.01` on every legal draw**, enforced by the template's own `constraint`.
   - The ceiling: `verification/verify.py:52` compares brute-force output **unscaled** against `1e-9`. B2's answers were integers and exact in float; these are not. TS float rounding runs about `|answer| · 1e-15`, so at 1e6 the gate becomes a coin flip and at 1e7 it fails on correct problems. The requirement is the ceiling itself — `|answer| <= 1e4`, with float exactness holding against that unscaled `1e-9` — not any particular payoff size. What makes payoff size the thing to watch is that variance scales as the *square* of the payoff: a payoff of 100 already puts a variance answer at the ceiling, while the same payoff in a plain-EV problem lands two orders of magnitude below it. So **"payoffs at or under 100" binds on variance and sd templates (Tasks 3-5); on plain-EV templates it is guidance, not a cap** — an EV problem may carry a larger prize, stake or label provided its own `constraint` holds `|answer| <= 1e4` and the author has measured the range rather than assumed it. Task 2 shipped `raffle-fair-price` drawing a grand prize up to 500 and `labeled-tickets-draw` printing labels up to 281; both peak at `|answer| <= 150.5` with zero brute-vs-exact mismatches across all 18,180 legal draws, which is what the rule actually asks for.
   - The floor: a zero or near-zero expectation breaks grading three ways (spec §3). `grade.ts:5` turns `rel` into strict float equality at `expected === 0`; `emit.ts:43` rejects every positive `abs` tolerance there; and the band `0.005·|answer|` starves as the answer shrinks.
   - Other `params`/`derived` values inherit B2's `[1e-6, 1e9)` window. The lower bound and the 1e15 cap are machine-enforced at `emit.ts:46`; the 1e9 ceiling is not.
   - **Write the floor as the requirement, not as a magic threshold.** `constraint: (p) => evOf(p) <= -0.01` says what constraint 2 demands; `<= -0.05` says a number nobody can trace back to a rule. Pick the bound from `|answer| >= 0.01` and let the draw space fall where it falls — where every answer is a multiple of some `1/n`, the floor binds at that `1/n` anyway and the literal never bites.
   - **The answer formula lives in exactly one place.** `ProblemTemplate.constraint` is `(p: Params) => boolean` and never sees `derived` (`packages/engine/src/problem.ts:24`), so pinning the floor tempts you to re-type the whole expectation inside `constraint`. Extract a module-local helper — `const evOf = (p: Params) => ...` — and call it from both `constraint` and `derived`. All 30 problems pin their floor this way, so the alternative is 30 files each carrying a second copy of their own answer formula, and the variance ones are long. Module-local only: this does not license a shared import between problem modules (see File structure).

3. **A fair game is asked as a price, never as an EV.** "What stake makes this fair?" / "what is the re-roll worth?" / "what premium breaks even?" have nonzero answers. "What is the EV of this fair game?" has the answer `0`, which constraint 2 forbids.

4. **Tolerance is `{ rel: 0.005 }` on all 30. Never `abs`.** The gate `emit.ts:43` runs inside the per-seed loop, so an `abs` tolerance must satisfy the **smallest** `|answer|` across all 100 draws — you would have to enumerate the draw space to pick one safely. Never `{ abs: 0 }`: an expectation is a decimal the solver rounds, and `registry.test.ts` pins the count of `abs: 0` problems at 15 (counting's exact counts).

5. **Every number in statement or solution text must be traceable** to `params`, `derived`, or `constants`. The audit at `emit.ts:25-26` tokenizes bare digit runs. Two consequences specific to this batch:
   - Intermediates named in prose (`n - 1`, a break-even payout, a leg of the sum) must be added to `derived`.
   - **Variance and sd templates must declare `constants: [2]`** (often `[1, 2]`). The exponent in `E[X^2] - (E[X])^2` and in `\sigma^2` is a bare `2` and is not otherwise traceable.

6. **`brute()` must never re-call the template's closed form.** `E[X] = np` re-typed in Python is transcription, not verification — it passes every gate while proving nothing. Every problem is assigned an independent path in its task table. `exact()` is the opposite: it *should* mirror the template, and **must stay in plain floats** — a `Fraction`-based `exact()` would absorb a template that loses precision, which is what the double-entry exists to catch. `brute()` uses `Fraction` where the space is rational and returns `float(...)` explicitly.

7. **Enumerate only under ~10⁵ atoms.** `verify.py` sets `BF_INSTANCES = 25`, so `brute()` runs 25× per problem. Above that, use a DP, a convolution, or a linear system.

8. **≥ 12 distinct answers, counted at the grading tolerance.** With `rel: 0.005` the band scales with the answer, so large answers collapse: a variance of 400 carries a band of 2.0, and draws giving 400 and 401 are one answer. Enumerate the legal draw space and count survivors **before writing prose**. Spec §6 names the three templates measured to be at risk, and the two that look at risk but are not.

   **The counting rule, written out because two implementers already diverged on it.** Tasks 2 and 3 each reported this number under a different rule, differing by up to a factor of eleven on identical data. This is the rule:

   > Enumerate **every legal draw** and take its answer. Sort the answers. Each answer `v` carries the grading interval `[v(1−0.005), v(1+0.005)]`. Two answers are the same answer when their intervals **overlap** — for sorted neighbours `a ≤ b`, when `b − a ≤ 0.005·(|a| + |b|)` — and the merge is **transitive**, so a run of overlapping neighbours collapses to one. The count is the number of runs.

   **Do not re-implement any of this.** `content/problems/draw-space.test.ts` exports `legalAnswers`, `distinctAtBand`, `emittedSpread` and `neighbourDensity`, self-tested against deliberately broken inputs, and runs the floors below over every ev-variance template as a committed gate. Full enumeration of all sixteen shipped templates — 614,558 draws — takes 180ms, so there is no reason to sample and no reason to write a second copy. Every reimplementation in this batch has produced a plausible wrong number: a replayed chain checker reported 71.9% where the truth was 25.5%, and a re-added `toPrecision(12)` invented 52 mismatches that do not exist.

   Two things that are not that rule and must not be substituted for it. **Keeping a value whenever it falls outside the band of the last value kept** is non-transitive and much looser — on `sum-of-bets-variance` it reports 509 where the rule above reports 47. **Counting over the 100 emitted instances** is a different scope, not a different rule, and is capped at 100 by construction; a number in that scope can never be compared with a number in this one.

   **The floor is not the target, and it does not measure what a drilling user feels.** `>= 12` catches *answer collapse*; it does not catch a small draw space. Task 2 shipped `indicator-match-count` at 17 distinct answers — compliant — on a space of only 20 legal draws, so each parameter tuple recurred about five times across the 100 emitted instances and a learner met the same sentence twice in a session. It was widened in review to 580 draws and 123 distinct answers. So measure two further numbers before writing prose, because the repeat rate is what the user actually experiences:
   - **distinct problem texts per 100 emitted instances** — count distinct `params` tuples, not distinct answers; and
   - **the most-repeated tuple's count**.

   **Distinct texts per 100 and the most-repeated count are the primary bar**, and the distinct-answer floor is the legacy one. The first two are unambiguous, need no merge rule, and are what a drilling learner actually meets in a session; the answer count is a proxy for collapse that a wide, densely packed range can understate badly. Read them in that order.

   Measured across the eight problems shipped in Tasks 1-2. **The first three columns are per-100-emitted-instances**, which is why the answer counts in column three top out below 100; column four is the full-legal-space count under the rule above, and is the one to compare a new template against:

   | | distinct texts / 100 | most repeated | distinct answers, per 100 | distinct answers, full space |
   |---|---|---|---|---|
   | best (`raffle-fair-price`, `profit-net-of-cost`) | 100 | 1 | 82 / 64 | 81 / 275 |
   | **median — this is the target** | ~92 | 2 | ~64 | ~90 |
   | thinnest (`sum-of-two-draws`) | 70 | 4 | 31 | 36 |

   The thinnest row is **a floor that exists because it shipped, not a standard to aim at**. `sum-of-two-draws` is compliant and is deliberately not being reopened; do not read it as permission to land there. A payout or rate multiplier is this batch's established way to widen a space cheaply — it multiplies the draw count without touching whatever `brute()` has to enumerate.

   Task 3's eight, under the same two units:

   | slug | texts / 100 | most repeated | answers, per 100 | answers, full space |
   |---|---|---|---|---|
   | `two-outcome-variance` | 97 | 2 | 50 | 67 |
   | `spinner-pmf-variance` | 99 | 2 | 77 | 119 |
   | `affine-scaling-sd` | 98 | 2 | 69 | 88 |
   | `push-branch-bet` | 100 | 1 | 87 | 206 |
   | `sum-of-bets-variance` | 100 | 1 | 78 | **47** |
   | `urn-choice-total-expectation` | 99 | 2 | 72 | 92 |
   | `max-of-two-dice` | 97 | 2 | 90 | 172 |
   | `one-optional-reroll` | 95 | 2 | 81 | 96 |

   **The full-space count has a validity condition, and `sum-of-bets-variance` sits outside it.** Transitive interval overlap measures *range connectivity*, not distinguishability, and connectivity saturates on any space dense relative to its band. Check this before reading the number at all: **compare the mean gap between neighbouring distinct answers against the band width at the median answer. Once the mean gap drops below that width, the count is collapsing toward 1 and carries no information about the template** — and texts-per-100 becomes the only meaningful reading. `neighbourDensity`'s `saturated` flag is exactly this test, so it costs one call.

   Measured on `sum-of-bets-variance`: 2,224 distinct answers over [2.88, 200], mean neighbour gap **0.0887** against a band width of **0.627** at the median answer of 62.7 — seven times inside the condition — and the largest single merged run swallows **2,000 of the 2,224**, spanning [18.45, 177.8]. A tenfold range reported as one answer is not the metric understating; it is the metric measuring the wrong property. The hundred instances a learner is actually served carry 100 distinct texts and 78 distinct answers, and that is the true reading of this template.

   Those distinct-answer counts are deduped at `1e-9`. Counting by raw float identity gives 2,341 with a largest run of 2,110, because 117 of the values differ only in the last bit. That is the third unpinned numeric convention in this batch to produce a plausible wrong number, after the two merge rules and the two scopes — which is why `neighbourDensity` takes the dedupe tolerance as an argument rather than assuming one.

   A low full-space count on a saturated space is an artefact of the measure; a low texts-per-100 count is always a real defect.

## Authoring contract (applies to every problem in Tasks 2–5)

1. `id` = `ev-variance/<slug>`, `topic: "probability/ev-variance"`, `version: 1`. Params satisfy constraint 8 above; `constraint` also enforces constraint 2's floor and ceiling and rejects degenerate draws.
2. Every intermediate number lives in `derived`; the answer is one `derived` key named by `answerKey`; tolerance per constraint 4.
3. Statement is plain prose, all numbers via `fmtNum`/`pc`, no literal `$` (constraint 1). Solution is 3–6 steps ending with a step titled **Sanity check**. Per B2's contract, the Sanity check must compute something genuinely independent where it can be done cheaply — a check assembled from the answer's own inputs still reads as true when the answer is wrong. In this batch the natural independent check is usually a **break-even price**: derive the stake or payout that would make the game fair from different `derived` keys than the answer, then assert the offered terms sit on the losing side of it. That check visibly fails if the expectation's sign is wrong.
4. `keyInsight` and `commonTrap` contain no digits. `firms` and `expectedPaceS` set. `source` records `kind` plus `inspiration` honestly.
   - **What `kind` has meant across the first 16 problems, recorded so it stays consistent.** `textbook` when the template reproduces a *named* classic more or less as it is posed — `indicator-match-count` is the coat-check matching problem. `original` when the framing, the parameters and the question asked are the author's, even where the underlying idea is thoroughly well known — `binomial-mean` and `max-of-two-dice` are both standard interview fare and both `original`, because the surface and the ask are written here. Either way `inspiration` names the underlying classic in plain words, so the `kind` label never has to carry the honesty on its own.
   - **Both are checked as committed predicates, and a new problem must add its own.** `content/problems/prose-claims.test.ts` holds one `CLAIMS` entry per template — every `keyInsight`, `commonTrap` and Sanity-check assertion, evaluated on printed values over the full legal draw space. Extend it by copying an entry: each claim needs `says`, `holds`, and a mandatory `breaks` falsifier, with `exceptions` carrying the exact count where a claim is deliberately hedged. A 2 percent perturbation of the answer must be caught by at least one of a template's own claims, which is what stops a set of claims that only ever pin a sign.
   - **Both must be true on every legal draw, not merely on the typical one.** A param range is a set of problems, not one problem. Task 1's exemplar shipped a `keyInsight` about "a generous win on a rare branch" that reverses on 20 of its 289 draws, and a `commonTrap` accusing the solver of assuming the branches are equally likely on 55 draws where they provably are. Enumerate the draw space, look at each end, and state only the lesson that survives all of it.
   - **Phrase the trap so it stays a mistake everywhere.** "Judging the bet by which amount is larger" is not a trap where the two branches are equally likely — the comparison gives the right sign there. "Reporting that difference as the expected profit" still is, because it names a wrong number rather than a wrong preference. Hedge the claim honestly when you write it down: here the naive difference happens to land exactly on the expectation on 6 of 289 draws (wherever `l = 2w` at `k = 5`, plus one draw at `k = 6`), so the shortcut is unjustified everywhere but not *numerically* wrong everywhere. That is still a trap — a method that is right by coincidence is not a method — but do not assert a universality you have not enumerated. Aim the trap at a wrong *answer*, not at a wrong *intuition*.
5. **Prose must read naturally at both ends of every param range**, not just in the middle. Draw the extreme values and read the rendered sentence. Task 1's exemplar shipped "If it shows 6 or higher" on a six-sided die, which rendered on 42 of 100 instances; reframing the losing side as a strict inequality ("if the roll comes up below `k`") reads cleanly across the whole range. Watch plural agreement too — "the remaining 1 faces win" is the same class of bug.
6. **Displayed arithmetic uses exact operands, never rounded decimals.** This batch runs on sixths and thirds, so a chain built from printed decimals drifts off its own printed result: `$0.8333\times9=7.5$` really computes 7.4997, and `$7.5/0.1667=45$` gives 44.99. The answer is unaffected — it comes from the float `derived` — but a learner recomputing from the operands on screen lands somewhere else. Keep the fraction symbolic (`$\frac{5}{6}\times9=7.5$`) or reduce to integers over a common denominator (`$\frac{5\times9-1\times12}{6}$`). What is safe is not a particular *operation* but a chain whose **operands** are exact — plain integers or a symbolic fraction — with rounding applied only to the displayed result. `$2/6=0.3333$` is fine because `2` and `6` are exact, not because division is safe. Every operation drifts once its operands are rounded, subtraction emphatically included: measured over this exemplar's 289 draws, differencing the two printed legs disagrees with the printed answer on **66 draws by up to 0.200%**, which is *worse in relative terms* than the quotient case (105 draws, 0.030%) — e.g. `$1.333-1.667=-0.334$` where `ev` prints `-0.3333`. Do not read "use a fraction" as "avoid division"; read it as "never feed a rounded number into the next step." Sweep the legal draw space and assert `fmtNum` of the exact rational equals `fmtNum` of the float for every value you print.

   **The rule does not stop at one chain: a claim relating two *separately printed* values must also hold at displayed precision.** Everything above governs the operands *inside* a single `$...$`. A sentence that reconciles one printed figure against another is the same defect one level up, because each figure carries its own independent rounding. Measured on Task 2's `die-payoff-table`: the Sanity check asserted that the printed plain average moved by the printed shift to reach the printed expectation. Every individual chain had exact operands and the problem passed every gate — yet the displayed decimals fail to reconcile on **1657 of 6498 legal draws (25.5%)**, worst case `16.33 + 1.833` rendering `18.16` against a printed answer of `18.17`. The word "exactly" is what turns a rounding artifact into a false claim. Fix it by reconciling in integer numerators over a common denominator, or by claiming only a **direction** — a direction is safe when the true gap exceeds the printing resolution, which is worth measuring rather than assuming (here the gap is at least a sixth against a resolution of 0.01).

   **Harness rule: evaluate these predicates on `fmtNum` output, never on the underlying floats.** A sweep that checks `plainAvg + shift === ev` in float arithmetic reports clean on precisely the draws where the rendered page is wrong — that is how the defect above survived a sweep that reported all-green. Compare `Number(fmtNum(x))`, and additionally parse every rendered `$...=...$` and evaluate each side from its **printed literals**, so the assertion is about what the learner actually sees. Task 2's rebuilt harness runs 100,638 such chains across the seven problems. Two further harness rules earned the hard way: never leave a predicate stubbed as `() => true` (one shipped, and the claim it was supposed to cover went unverified while the report said otherwise), and mutation-test the checker itself — a checker that has never reported a failure has not been shown to be capable of one.
7. Prefer answers that are rationals with small denominators. `rel: 0.005` demands three significant figures, so an EV of `-1/6` must be typed `-0.167` — but `parseAnswerExpr` accepts `-1/6` exactly, and that is the route a solver who worked in fractions will take.
8. Python counterpart ships in the same commit, per constraint 6.
9. Registered in `content/problems/index.ts` `PROBLEMS` and in `verification/solvers/ev_variance.py` `SOLVERS`.

- [ ] **Step 1: Write the template**

Create `content/problems/ev-variance/two-outcome-bet.ts`:

```ts
import type { Params, ProblemTemplate } from "@qp/engine";
import { fmtNum } from "../util";

// The answer formula, written once. `constraint` only ever sees `params`
// (packages/engine/src/problem.ts:24), so without this helper the expectation would be
// typed twice — once to pin the answer away from zero, once to derive the answer.
const evOf = (p: Params) => ((7 - p.k) * p.w - (p.k - 1) * p.l) / 6;

// The house-edge opener, and the batch's first negative answer. `winFaces` and
// `loseFaces` exist so the prose can name the numerators of the two probabilities and
// keep the displayed arithmetic in exact sixths; `fairWin` exists so the Sanity check
// can price the bet independently of `ev`.
// Amounts are spelled "dollars" in words — a literal $ is a KaTeX delimiter.
export const twoOutcomeBet: ProblemTemplate = {
  id: "ev-variance/two-outcome-bet",
  version: 1,
  topic: "probability/ev-variance",
  difficulty: 1,
  firms: [{ firm: "optiver", weight: 0.4 }, { firm: "sig", weight: 0.35 }],
  source: { kind: "original", inspiration: "single-roll house-edge bet whose payout looks generous and whose expectation is not" },
  params: {
    k: { range: { min: 3, max: 6, step: 1 } }, // rolls below k lose
    w: { range: { min: 2, max: 12, step: 1 } },
    l: { range: { min: 2, max: 12, step: 1 } },
  },
  // Strictly a losing bet, held at or past the batch's answer floor of |answer| >= 0.01:
  // a fair game would make the answer 0, which grades as strict float equality and fails
  // the abs-tolerance gate. Every ev is a multiple of 1/6, so the floor actually binds at
  // -1/6 and no draw sits near it. k starts at 3 because k = 2 loses on one face in six
  // and is almost never a losing bet.
  constraint: (p) => evOf(p) <= -0.01,
  derived: (p) => {
    const winFaces = 7 - p.k;
    const loseFaces = p.k - 1;
    const pWin = winFaces / 6;
    const pLose = loseFaces / 6;
    const winLeg = pWin * p.w;
    const loseLeg = pLose * p.l;
    return { winFaces, loseFaces, pWin, pLose, winLeg, loseLeg, fairWin: loseFaces * p.l / winFaces, ev: evOf(p) };
  },
  statement: (p) =>
    `A fair six-sided die is rolled once. If the roll comes up below ${fmtNum(p.k)} you lose ${fmtNum(p.l)} dollars; ` +
    `otherwise you win ${fmtNum(p.w)} dollars. What is your expected profit, in dollars, on one roll?`,
  answerKey: "ev",
  accepted: { tolerance: { rel: 0.005 } },
  solution: (p, d) => [
    { title: "Setup", body: `Expected profit weights each outcome by its probability. A roll below ${fmtNum(p.k)} loses, which is ${fmtNum(d.loseFaces)} of the 6 faces, so the lose probability is $${fmtNum(d.loseFaces)}/6=${fmtNum(d.pLose)}$; that leaves ${fmtNum(d.winFaces)} of the 6 faces to win, a win probability of $${fmtNum(d.winFaces)}/6=${fmtNum(d.pWin)}$.` },
    // Every chain below keeps the sixths as exact fractions. Multiplying the rounded
    // decimals instead ($0.8333\times9$) drifts off the printed result — and so does
    // subtracting them, which is why Combine reduces to integers over 6 rather than
    // differencing the two printed legs.
    // The unit trails the math in these steps: leading with it would render "1 dollars"
    // wherever a leg or the expectation lands on one.
    { title: "Weight each branch", body: `Measured in dollars, the winning branch contributes $\\frac{${fmtNum(d.winFaces)}}{6}\\times${fmtNum(p.w)}=${fmtNum(d.winLeg)}$ and the losing branch takes away $\\frac{${fmtNum(d.loseFaces)}}{6}\\times${fmtNum(p.l)}=${fmtNum(d.loseLeg)}$.` },
    { title: "Combine", body: `Subtract the losing contribution from the winning one. Over a common denominator of 6 the arithmetic stays exact, giving an expected profit per roll, in dollars, of $\\frac{${fmtNum(d.winFaces)}\\times${fmtNum(p.w)}-${fmtNum(d.loseFaces)}\\times${fmtNum(p.l)}}{6}=${fmtNum(d.ev)}$.` },
    // At winFaces = 1 the division is a no-op, and \frac{·}{1} reads as a mistake rather
    // than a step: the sole winning face simply has to return the whole losing total.
    // winFaces = 3 keeps its fraction — there the cancellation IS the argument, since
    // equally likely branches make the fair payout equal to the loss.
    { title: "Sanity check", body: `Price the bet the other way round, counting faces rather than probabilities. To break even, the winning faces would have to return exactly what the losing faces take, so a fair payout per winning face is $${
      d.winFaces === 1
        ? `${fmtNum(d.loseFaces)}\\times${fmtNum(p.l)}=${fmtNum(d.fairWin)}`
        : `\\frac{${fmtNum(d.loseFaces)}\\times${fmtNum(p.l)}}{${fmtNum(d.winFaces)}}=${fmtNum(d.fairWin)}`
    }$ dollars. The game offers only ${fmtNum(p.w)}, short of that, so the expected profit must come out negative — and it does.` },
  ],
  keyInsight: "An expectation weights every outcome by how often it arrives, so a win and a loss only become comparable once each has been multiplied by its own probability — the raw sizes of the two payouts say nothing on their own about which way the bet leans.",
  commonTrap: "Subtracting the loss amount from the win amount and reporting that difference as the expected profit, which skips the step where each amount is scaled by the chance of actually landing on its branch.",
  expectedPaceS: 35,
  verify: { method: "brute-force" },
  constants: [6],
};
```

This draw space was enumerated before the plan was written, and these are the numbers to expect:

| property | measured | requirement |
|---|---|---|
| legal draws | 289 of 484 (59.7% acceptance) | `drawParams` retries 100× — never at risk |
| distinct answers | 58 exact, **58 surviving at the `rel: 0.005` band** | ≥ 12 (constraint 8) |
| `|ev|` range | 1/6 to 29/3 | ≥ 0.01 and ≤ 1e4 (constraint 2) |
| values outside `[1e-6, 1e9)` | 0 | none (constraint 2) |

- [ ] **Step 8: Write the Python counterpart**

Create `verification/solvers/ev_variance.py`:

```python
"""Independent Python counterparts for content/problems/ev-variance/*.
exact(): re-derives every TS `derived` value in plain float arithmetic (double-entry).
It is MEANT to mirror the template — that mirroring is the check — so it stays in
floats; a Fraction-based exact() would absorb a template that loses precision.
brute(): recomputes the ANSWER by enumerating the sample space, never by re-calling
the template's closed form. Only brute() carries the independence requirement, works
in Fraction where the space is rational, and returns float() explicitly."""

from fractions import Fraction


def two_outcome_bet_exact(p):
    k, w, loss = int(p["k"]), int(p["w"]), int(p["l"])
    win_faces = 7 - k
    lose_faces = k - 1
    p_win = win_faces / 6
    p_lose = lose_faces / 6
    win_leg = p_win * w
    lose_leg = p_lose * loss
    return {
        "winFaces": win_faces,
        "loseFaces": lose_faces,
        "pWin": p_win,
        "pLose": p_lose,
        "winLeg": win_leg,
        "loseLeg": lose_leg,
        "fairWin": lose_faces * loss / win_faces,
        "ev": (win_faces * w - lose_faces * loss) / 6,
    }


def two_outcome_bet_brute(p):
    """Walk the six faces and average the profit. No probabilities are formed and
    nothing is multiplied by a weight — the template's p*payoff structure never
    appears here, which is what makes this a second derivation."""
    k, w, loss = int(p["k"]), int(p["w"]), int(p["l"])
    total = Fraction(0)
    for face in range(1, 7):
        total += Fraction(w) if face >= k else Fraction(-loss)
    return float(total / 6)


SOLVERS = {
    "ev-variance/two-outcome-bet": {"exact": two_outcome_bet_exact, "brute": two_outcome_bet_brute},
}
```
